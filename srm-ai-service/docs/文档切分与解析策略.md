# 文档切分（Chunking）与解析策略手册

> 适用项目：VANPINE SRM `srm-ai-service`
> 目标：面对常见文档类型时，知道**普通情况怎么切**、**复杂情况怎么处理**、**坑在哪**。
> 最后更新：2026-11-10

## 1. 总原则（所有文档通用）

1. **结构边界优先，字符兜底**
   标题、条款、章节号、sheet、slide 是天然语义边界。先按结构切，结构块超长才退回「段落 → 句子 → 硬切」。纯递归字符切分不知道「第 X 条」是边界，会把相邻条款拼进同一块，是合同类文档答错的第一大原因。

2. **原子性**
   表格、代码块、签名块不可拆散。表格必须独立成块，并在超长时**重复表头**切行。

3. **可还原**
   每块必须携带：所属章节路径（heading_path）、页码（PDF）、块类型（para/clause/list/table）。这是引用展示和排障的基础。

4. **父子两层**
   子块小（300~400 token）用于**命中**，父块大（1000~2000 token）用于**喂上下文**。这是目前工业界的默认做法。

5. **不可解析要显式失败**
   扫描件抽不出文本时必须报「内容为空/疑似扫描件」，不能静默入库 0 个块——静默失败比报错更难排查。

6. **切分参数经验值（中文）**
   - 子块：300~400 token 为目标，512 为硬顶
   - 重叠：10%~15%（本项目 64 token ≈ 12%），**只在被强切时加**，结构边界处不加
   - 父块：1000~2000 token
   - 低于 96 token 的尾块并入同章节上一块，绝不跨章节

## 2. 按文档类型逐一说明

### 2.1 TXT 纯文本

**普通情况**
- 编码依次尝试 UTF-8 → GBK → Latin-1
- 空行是段落边界，连续正文行合段
- 段落超过 512 token 时按「空行 → 换行 → 。！？；，」递归切分
- 无结构的纯文本，**没有再好的办法**，能做的只有编码和段落

**复杂情况**
- 一整个文件只有一行（导出日志、JSON 串）→ 只能按标点硬切，可先格式化
- 中英混排 → token 估算要按字符类别加权（汉字 1 字 ≈ 1 token，英文 1 词 ≈ 1.3）
- 编码套娃（GBK 内容被当 Latin-1 存过）→ 先做 mojibake 修复再解码
- 无意义内容（base64、日志栈）→ 入库前做质量过滤

**坑**
- 用 `len()` 当 token 数：中文块会偏小、英文块会偏大
- 只按 `\n\n` 切：中文文档常常整段只有一个换行

---

### 2.2 Markdown

**普通情况**
- 按 `#` ~ `######` 构建标题树，`heading_path` 就是面包屑
- 标题本身**不单独成块**，并入其下第一段正文（避免产生纯标题的噪声向量）
- 同章节内贪心聚合到 384 token；换标题即换块
- 表格（管道表）作为原子块独立；列表保留为一整块

**复杂情况**
- HTML 内嵌表格 → 用解析器转 Markdown 表，不要当纯文本切
- 代码块（```）→ 整体原子，不拆；超长代码按函数边界切
- 标题跳级（`#` 直接到 `###`）→ 补齐缺失层级，防止面包屑断裂
- 超长章节（一个 `##` 下 5000 字）→ 章节内按段落二次聚合，仍然保持同一 heading_path
- 前置 YAML front matter → 抽取成元数据，不参与切分
- 每个块的**嵌入文本 = 文档名 > 标题路径 + 正文**（本项目已实现）：文档名和章节名因此也能被 BM25 关键词命中

**注意**：结构边界处不需要重叠（重叠=0）；overlap 只用于无结构文本或强制硬切。

---

### 2.3 Word (.docx)

**普通情况**
- **不要用正则猜标题**：docx 自带样式，`Heading 1~9` / `标题 1~9` 就是层级，直接拿来构建 heading_path
- 按 `document.element.body` 的**原始文档顺序**遍历段落和表格，否则表格会全部跑到文末
- 表格 → Markdown 管道表；超过 40 行按行组切片，每片重复表头
- 列表段落保留为独立 list 块

**复杂情况**
- **无样式标题**（人工排版，只加粗/放大字号）→ 需要按「加粗 + 短行 + 独立成段」启发式识别，或走 LibreOffice 转 PDF 后按字号识别
- **页眉 / 页脚**：python-docx 不读它们（在 section 里），要显式读 `section.header / footer` 并过滤；否则每页重复的公司名会污染所有块
- **批注 / 修订痕迹**：检索时通常不需要，入库前剔除 deleted 文本
- **文本框 / 艺术字**：普通遍历取不到，需要遍历 `w:txbxContent`
- **合并单元格**：python-docx 会重复返回被合并单元格的文本，转 MD 时需要去重，否则表格语义错乱
- **跨页表格**：Word 里是一个表，但页眉会插在中间；解析后需要按表头识别续页
- **多级编号**：`1.` `1.1` `(1)` 的编号由样式生成，`para.text` 里可能没有 → 需要读 `numbering.xml` 或接受编号缺失
- **自定义样式**：只按 `pStyle` 字符串判断会漏——要结合 `styles.xml` 里的 `w:name` 和 `w:outlineLvl`（大纲级别才是真正的标题语义）
- **修订痕迹**：`w:ins`（插入）/ `w:del`（删除）同时存在，必须显式选择接受或拒绝，否则会把已删除文字入库、或出现两个版本
- **批注**：`comments.xml` 用 `commentRangeStart/End` 锚定到段落，按需挂到所属块
- **脚注 / 文本框**：`footnotes.xml`、`w:txbxContent` 常被普通遍历漏掉，需要用 `docx2python` 等库抽取
- **docx 没有可靠页码**：页码是渲染结果，不要按页切分；需要页码时先转 PDF

**坑**
- 直接用 `docx2txt` 会把表格拍平成一行一行文本，表格结构全丢
- 用 `paragraph.style.name` 判断标题时，中文 Word 的样式名是「标题 1」不是「Heading 1」，正则要兼容
- 合并单元格（`gridSpan` / `vMerge`）解析后文本会重复或为空，转表前要先归一

**工具**：`python-docx`（基础）、`docx2python`（页眉页脚/脚注/文本框/批注）、`mammoth`（docx→Markdown）、`unstructured partition_docx + chunk_by_title`、`Pandoc`（修订接受/拒绝）、`LibreOffice headless`（转 PDF 拿页码）

### 2.4 电子版 PDF（有文本层）

**普通情况**
- pypdf 逐页 `extract_text()`，保留页码
- 标题优先级：**书签/大纲 > 字号启发式 > 条款正则**
- 字号启发式：全书字符字号取中位数作正文基准，字号 ≥ 中位 × 1.15 且行长 ≤ 40 字符判为标题
- 条款正则 `第X条 / 第X章 / 第X节` 作为硬边界
- 表格用 pdfplumber 的 `extract_tables()`，受控启用

**复杂情况**
- **分栏排版**（论文、手册双栏）→ 必须做版面分析按栏读取，否则左右栏文字会被交错拼成乱句。轻量方案：按 x 坐标聚类分栏；重方案：Docling / MinerU / RAGFlow DeepDoc
- **页眉页脚 / 页码 / 水印**：按「跨页重复出现的同一行」检测并删除（见第 3 节）；简单方案也可直接裁掉页面上下的 5%~8% 区域，但版式一变就失效，只适合固定模板
- **行尾连字符 / 硬换行**：英文 PDF 行尾的 `-` 要接回单词；中文 PDF 的每行换行是版式换行，要先合并成段再切
- **单页字符数 < 50**：基本可判定为扫描页，转 OCR 处理
- **跨页段落**：页末一行 + 下页开头一行要拼接，否则一句话被劈成两半
- **跨页表格**：下一页续表要识别表头并重复
- **脚注**：正文底部的小字会被混进正文，导致检索命中错误内容；需要按字号/位置识别脚注并单独标记
- **扫描页混排**：一份 PDF 里既有文字页又有图片页 → 逐页做文本密度检测，低密度页单独送 OCR
- **公式**：文本层通常是乱码，检索基本无效，建议保留图片
- **书签缺失**：用字号启发式；再不行用条款正则

**坑**
- `extraction_mode='layout'` 会插大量空格对齐列，把中文合同条款切碎——合同场景不要用
- 直接按字符数切：PDF 的换行是版式换行不是语义换行，必须先合并行再切

### 2.5 扫描件 PDF / 图片（OCR）

**先说 OCR 是什么**：扫描件本质是一张张图片，里面没有「文字」，只有像素。OCR（光学字符识别）就是让程序把图片里的字形识别回文本。没有 OCR 这一步，扫描件在 RAG 里就是空文档——检索永远检索不到。

**普通情况**
1. **逐页检测**：抽取文本层，若某页字符数 < 阈值（如 50 字/页）且页面有图片 → 判定为扫描页
2. **渲染**：用 PyMuPDF 按 200~300 DPI 渲染成图片
3. **预处理**：灰度、二值化、去噪、纠偏（去倾斜）
4. **OCR**：PaddleOCR / Tesseract / 云 OCR（阿里/腾讯/百度）
5. **版面分析**：识别标题/段落/表格区域，给出阅读顺序
6. **后处理**：合并断行、去除页眉页脚、修正常见错字
7. 之后与普通文本一样走结构化切分

**复杂情况**
- **表格**：普通 OCR 只给文字不给结构 → 需要表格识别模型（PaddleOCR PP-Structure、RAGFlow DeepDoc、云 OCR 表格接口），输出 HTML/Markdown 表
- **双栏 / 多栏**：必须做版面阅读顺序，否则左右栏交错
- **印章 / 手写 / 签名**：识别率低，建议只保留位置信息，不参与检索
- **倾斜 / 噪声 / 低分辨率**：先图像增强，识别置信度低时告警
- **混合文档**：正文是电子版、附件是扫描件 → 按页分流处理
- **质量校验**：OCR 后统计「有效字符比例」「识别置信度均值」「空页率」，低于阈值就判为解析失败并提示人工处理，不要静默入库垃圾
- **降级链**：本地 OCR（PaddleOCR）失败/低分 → 云 OCR（阿里/腾讯/百度）→ 多模态大模型兜底，逐页选择最优管线

**工具选择**

| 方案 | 适用 | 说明 |
|---|---|---|
| PaddleOCR / PP-Structure | 中文为主、自建 | 中文效果最好，支持版面+表格 |
| Tesseract | 简单英文文档 | 中文效果一般，需自己接版面 |
| 阿里 / 腾讯 / 百度 OCR | 生产环境 | 表格/印章/公式接口齐全，按量付费 |
| RAGFlow DeepDoc | 一站式 | 版面分析 + 表格 + OCR 全内置 |
| MinerU / marker | 学术 PDF | 公式、图表、阅读顺序强 |

**坑**
- 直接对整页图片喂 OCR 再切：页眉页脚和页码会混进每一块
- 200 DPI 以下识别率骤降，300 DPI 是甜点，再高收益递减
- 不做质量校验：扫描质量差的文档会往知识库里灌一整页乱码

### 2.6 Excel (.xlsx / .xls)

**普通情况**
- 每个 sheet 视为一个章节，sheet 名进 heading_path
- 首个非空行作表头
- 每 40 行数据成一组，转 Markdown 表，**每组重复表头**
- 单行最多 30 列，防超宽表把块撑爆

**复杂情况**
- **合并单元格**：openpyxl 读到的是左上角值 + 其余空 → 需要向下/向右填充
- **多行表头 / 两级表头**：先识别表头行数（连续非数据行），拼成「大表头_小表头」
- **宽表（>30 列）**：按列分组横向切，每片重复主键列
- **公式**：`data_only=True` 只能拿到 Excel 保存时的缓存值；从未打开保存过的文件公式值为空 → 需要提示用户「请用 Excel 另存一次」
- **日期 / 数值**：`str(v)` 可能得到 `45291` 这类序列号 → 需要按单元格格式转换
- **隐藏 sheet / 草稿 sheet**：入库前过滤 `sheet_state != 'visible'`
- **合计 / 小计行**：检索价值低且干扰数值问答，可标记或过滤
- **一 sheet 多张表**：按空行或重复表头切子表，每张子表独立成块
- **超大表（10 万行）**：必须分组切片；同时考虑「行级句子化」
- **块大小**：每块 20~50 行（本项目 40 行），表名 / sheet 名 / 表头前缀控制在 50~100 token

**强烈建议：行级句子化**
把一行数据拼成一句自然语言，检索命中率会显著提升：

```
原始行：| 供应商编码 | 名称 | 等级 | 状态 |
        | SUP001 | 华东精密 | A | 合格 |
句子化：供应商 SUP001，名称 华东精密，等级 A，状态 合格。
```

因为用户问的是「华东精密是什么等级」，语义向量对「表格 + 竖线」的表征很弱，对自然语言句子表征很强。

### 2.7 PPT (.pptx)

**普通情况**
- 每页 slide 一块：标题 + 正文占位符 + 演讲者备注
- 页码、母版页脚过滤
- slide 标题进 heading_path

**复杂情况**
- 图表 / SmartArt / 图片 → 普通提取拿不到文字，需要渲染成图后 OCR 或走多模态描述
- **图表数据**：`python-pptx` 可以直接读 chart 的 category/series 数据，转成表比 OCR 可靠
- 以图为主的 demo PPT → 文字量极少，RAG 价值很低，建议入库时标注「低文本密度」
- 关闭的隐藏页 → 默认跳过
- 一页形状很多时按「标题 → 正文 → 表格 → 备注」的顺序拼接，不要按形状遍历顺序乱拼

---

### 2.8 HTML / 网页

**普通情况**
- 用正文提取库（trafilatura / readability）去掉导航、广告、评论、脚本
- 按 `h1~h6` 建标题树切分
- 表格保留为 Markdown

**复杂情况**
- SPA / 动态渲染 → 需要无头浏览器（Playwright）渲染后再提取
- 同一内容多版本（移动版/打印版）→ 入库前去重
- 代码块、引用块 → 原子处理
- **工具**：`trafilatura` / `readability`（正文提取）、`BeautifulSoup`（结构解析）、`LangChain HTMLHeaderTextSplitter`（标题树切分）

---

### 2.9 合同（复杂文档高频）

**普通情况**
- `第X条 / 第X章 / 第X款` 是硬边界，绝不跨条合并
- 条款标题 + 其下款项合为一块（384 token 内）
- 表格（报价单、交付清单）原子化

**复杂情况**
- **交叉引用**：「见第 5 条」「按附件二执行」→ 把被引用条款号抽成元数据，检索时补查
- **主合同 + 附件 + 补充协议**：独立文档入库，用关联 ID 串起来，检索结果里标注版本关系
- **签署页 / 盖章页**：信息密度低，可单独成块并标记 chunk_type=signature
- **版本对比**：旧版与新版同时入库会导致答案冲突 → 用 `is_current` 元数据过滤，只让当前版本参与检索
- **金额 / 日期 / 当事方**：抽成结构化元数据，用于过滤和精确问答
- **OCR 合同**：印章区域识别后要剔除，否则会污染正文

**坑**
- 用字符切分把「第 5 条」和「第 6 条」拼进同一块 → 回答张冠李戴
- 条款号（HT-2024-001）被分词器拆开 → BM25 命不中，需要保留整词（本项目 tokenizer 已按整词处理）

### 2.10 技术手册 / 规格书

**普通情况**
- 章节号 + 编号列表为结构
- 参数表原子化，表头重复
- 图示标题（图 3-1 说明）作为独立说明块

**复杂情况**
- 交叉引用（「参见 4.2 节」）
- 多语言版本 → 只入库一种语言，或加 `lang` 元数据隔离
- 单位 / 量纲 → 保留原文，不要自动换算
- 版本号 → 元数据过滤

---

### 2.11 制度 / 法规 / 标准

**普通情况**
- 章节 + 条款硬边界
- 条款号必须作为可检索元数据（用户经常直接问「第 12 条怎么规定的」）

**复杂情况**
- 修订记录、附录、引用其他法规 → 单独成块并标记类型
- 生效 / 废止日期 → 元数据，检索时默认只查现行版本
- 一个条款被多处引用 → 保持条款原样，不要被父块合并打散

---

### 2.12 财报 / 年报

**普通情况**
- 章节 + 表格

**复杂情况**
- 跨页大表（资产负债表）→ 必须合并跨页表并重复表头
- 合并口径 / 母公司口径 → 表名进 heading_path，防止混淆
- 脚注编号（①②③）→ 脚注与正文分离，正文保留编号
- 单位（千元 / 百万元）→ 抽成元数据，问答案时用
- 图表 → 多模态描述或跳过

---

### 2.13 邮件 / 工单 / 聊天记录

**普通情况**
- 每条消息一块，带 `from / to / time / 主题` 元数据
- 同一会话按时间排序

**复杂情况**
- 长线程 → 按主题聚合，或对每个会话生成摘要块
- 引用历史（`>` 前缀）→ 去重，只保留最新正文
- 附件 → 单独解析并与邮件关联

---

### 2.14 图片 / 图纸 / 影印件

- 纯图片**无法**被文本检索命中，只能：
  1. OCR 提取图上文字（效果取决于清晰度）
  2. 多模态模型生成描述（成本高）
  3. 入库但不参与检索，仅作附件下载
- 工程图纸、电路图、平面图：文字量少、专业符号多，OCR 收益低，**建议只存不检索**
- 图片说明（caption）如果能抽到，是比 OCR 更好的检索入口

## 3. 文档特有元素的处理（跨类型通用）

### 3.1 页眉 / 页脚

**识别规则（组合判定）**
1. 同一行文本在 ≥ 30% 的页面的**首 N 行或末 N 行**重复出现
2. 位于页面上下边距区域内（y 坐标在页高 8% 以内或 92% 以外）
3. 命中页码正则：`^\d+$`、`^第\s*\d+\s*页`、`^\d+\s*/\s*\d+$`、`^-\s*\d+\s*-$`

**处理**
- 页眉页脚：删除
- 页码：删除，但页码信息保留在块的 `page` 元数据里
- 水印（斜向重复文字）：按文本内容匹配删除

### 3.2 目录（TOC）

- 特征：行尾有点线 + 页码（`.... 12` / `··· 5` / 多个空格 + 数字）
- 整段连续目录行合并为一个 `toc` 块，**不入库**
- 目录页的标题不能作为正文块

### 3.3 脚注

- 特征：页面底部、字号小于正文、以 `①` 或数字上标开头
- 处理：从正文剥离，作为块的附属元数据或单独块，避免污染正文检索

### 3.4 表格

- 一律原子化，不与其他文本合并
- 超硬顶时按行切，**每片重复表头**
- 非标准结构（缺分隔线）→ 退回递归切分，不要按行乱切

### 3.5 跨页内容

- 段落：页末行与下页首行拼接（判断是否以句末标点结束）
- 表格：识别续表（重复表头）后合并
- 列表：跨页列表延续

### 3.6 分栏

- 双栏/多栏文档必须按栏读取
- 轻量方案：按字符 x 坐标聚类，先读左栏再读右栏
- 准确方案：Docling / MinerU / DeepDoc 版面分析

## 4. 文档类型识别

不要只信扩展名，三层判定：

1. **魔数（magic bytes）**

   | 类型 | 文件头 |
   |---|---|
   | PDF | `%PDF` |
   | DOCX / XLSX / PPTX | `PK\x03\x04`（zip） |
   | DOC / XLS / PPT（旧版） | `\xD0\xCF\x11\xE0` |
   | RTF | `{\rtf` |
   | HTML | `<!DOCTYPE html` / `<html` |

2. **内容探测**
   - PDF：逐页统计文本层字符数 → 判定「电子版 / 扫描件 / 混合」
   - DOCX：检查是否存在 `Heading N` 样式 → 判定「有结构 / 无结构」
   - Excel：检查 sheet 是否全为表格 → 判定「表格型 / 混合型」

3. **结构探测**
   - 是否有书签、是否有标题样式、是否有目录、是否双栏

识别结果写入文档元数据，后续切分策略按类型选择。

## 5. 复杂文档的进阶策略

### 5.1 父子块（本项目已实现）

- 子块（约 384 token）进向量库，负责**命中**
- 父块（约 1200 token）按同一 heading_path 聚合，存 MySQL，负责**上下文完整**
- 检索流程：混合召回子块 → rerank → 按 parent_id 回填父块 → 二次 rerank

### 5.2 上下文增强（Contextual Retrieval）

每个块入库前，让 LLM 生成一句「这个块在整篇文档中的位置与作用」，拼在块前面再向量化：

```
[上下文] 本文是华东精密 2026 年度采购框架协议的第 4 条，规定违约金计算方式。
[正文] 4.1 乙方逾期交货的，每逾期一日按合同总额的 0.5% 支付违约金……
```

Anthropic 的报告显示，这一招可显著降低检索失败率（配合 BM25 效果更好）。成本是一次性 LLM 调用，可按文档批量做。

### 5.3 Late Chunking

先用长上下文 embedding 模型对全文编码，再做池化切块，使每个块的向量都携带全文语境。工程实现复杂，通常不必要。

### 5.4 元数据过滤

为每块携带：租户、文档类型、版本、生效日期、章节路径、页码、条款号。检索时先过滤再召回，能消掉大量「版本冲突」类错误。

### 5.5 评估

建 30~50 条「问题 → 应命中的原文片段」的 golden set，每次改切分/检索都跑一遍 Recall@k、MRR。没有评估集的调参都是盲调。

## 6. 市面框架对比

| 框架 | 强项 | 弱项 | 适用 |
|---|---|---|---|
| **Unstructured** | 格式覆盖最广（几十种），分块策略齐全 | 版面/表格深度一般，重服务部署 | 多格式混合场景 |
| **RAGFlow DeepDoc** | 版面分析 + OCR + 表格识别一体化，开箱即用 | 重，依赖多 | 想要一站式复杂文档处理 |
| **Docling（IBM）** | PDF 版面/表格/阅读顺序强，本地可跑 | 扫描件需外接 OCR | 电子版 PDF、学术文档 |
| **MinerU** | 学术 PDF、公式、图表 | 中文商业文档适配一般 | 论文、技术资料 |
| **marker** | PDF → Markdown 质量高 | 速度慢、GPU 依赖 | 高质量转换 |
| **PyMuPDF4LLM** | 轻量、快、PDF → Markdown | 无 OCR、无复杂版面 | 轻量集成 |
| **LlamaParse** | 云端、格式多、表格强 | 收费、数据出域 | 商业项目快速接入 |
| **Azure Document Intelligence / Textract / Google Document AI** | 表格、表单、手写极强 | 收费、数据出域 | 生产级高准确率要求 |

**建议路线**
1. 现阶段：保持轻量（pypdf + python-docx + openpyxl），把结构切分做扎实
2. 下一步：引入 PyMuPDF4LLM 或 Docling 处理复杂 PDF
3. 扫描件：按量选择云 OCR（省心）或 PaddleOCR（自建）
4. 不建议一上来就上重型框架，先把评估集建起来，再按需升级

## 9. 一句话总结

> **普通文档靠结构切（标题、条款、表格边界），复杂文档靠版面分析（阅读顺序、页眉页脚、表格、OCR）；扫描件没有 OCR 就等于没有入库。**
